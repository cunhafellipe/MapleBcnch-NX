## 1. 地圖結構：橫向平面，但不是只有橫向

### 1.1 三種尺寸型態（實測）

| 型態 | 比例（寬/高） | 實例 | 用途 |
|---|---:|---|---|
| **極橫條** | 8.5 ~ 13.7 | 海盜試煉場、怪異回廊 | 通道、走廊、跑酷段 |
| **橫向** | 1.1 ~ 4.3 | 蘑菇村、東部岩山 | 一般城鎮、野外（最常見） |
| **縱向** | 0.6 ~ 0.9 | 深海峽谷、開往聖地 | 垂直下降、峽谷、井 |

> **關鍵修正**：「橫向平面」是**主流但不是唯一**。
> 深海峡谷比例 0.6、高 2074px——垂直下降型地圖同樣常見。
> 生成器必須先決定**型態**，再決定結構。

### 1.2 8 層結構是固定的

所有實測地圖都是 **layer 0..7**，且分工一致：

| 層 | 實測用途 | 備註 |
|---|---|---|
| 0 | 主地面（`tS` = tile set 名） | 最主要的地面層 |
| 1 | 第二地面 / 次要地面 | 同圖可與 L0 共用 set |
| 2–5 | 中景物件、裝飾 | 東部岩山 L2/L3 都用 `dryRock` |
| 6–7 | 前景、遮罩 | 連接件 `connect*` 常在此 |

**觀察到的重要規律**：**同一張地圖的不同圖層可以共用同一個 tile set**
（東部岩山 L2、L3 都是 `dryRock`）。這代表 tile set 的選擇是**按場景**，
不是按圖層。

**與重力的關聯（重要）**：foothold 的 `layer` 欄位**跟著視覺圖層走**，
不是固定值。東部岩山 foothold 橫跨 L0–L3，深海峡谷則全在 L4。
詳見第 5.2 節規則一。

### 1.3 Link stub：有些地圖是空殼

3 張抽樣地圖回報 `hasGeometry: false` 且帶 `link` 欄位：

```
105040348 隐藏地图 : 倒塌的巨人城池 → link: 105040320
```

**這些地圖的幾何資料在目標地圖裡**，本身只有門戶與腳本。
API 回傳的是 stub 內容，不是空地圖。

> **對生成器的意義**：讀到 `link != null` 時，必須跟到 `link` 目標去讀結構，
> 否則會把 stub 誤判成「空地圖」並生成一個沒有重力的空殼。

## 2. 地圖風格：地面素材

### 2.1 現有素材庫（`Map.nx`）

- **Tile set：109 個**，全部在 `Map.nx` 的 `Tile/` 節點
- 範例：`brownBrick`、`grassySoil`、`dryRock`、`snowyDarkrock`、`deepSeeFloor`、
  `poisonForest`、`sandySeaFloor`、`woodCave`、`moltenRock`…（完整清單見 palette 端點）

素材已按主題命名，**命名本身就是風格詞彙表**：

| 關鍵字 | 風格 |
|---|---|
| `Brick` / `Marble` / `Subway` | 人工建築 |
| `Soil` / `Grass` / `Leaves` / `Forest` | 自然植被 |
| `Cave` / `Mine` / `Rock` / `DryRock` | 洞穴礦坑 |
| `Snow` / `Ice` | 冰雪 |
| `Sand` / `Desert` | 沙漠 |
| `See` / `Water` / `River` | 水域 |
| `Magatia` / `Masteria` | 特定地區主題 |

### 2.2 地面 vs 物件的分界（實測）

**關鍵發現**：一張地圖的視覺組成可以是

- **tiles 為主**（蘑菇村 40 tiles / 0 objs）→ 用 tile set 平鋪
- **objs 為主**（深海峡谷 0 tiles / 158 objs）→ 用物件堆疊

**兩種都要支援**。`ancientForest` 這類「全是 foothold/portal 邏輯節點、
沒有視覺 canvas」的 set 屬於陷阱，詳見第 6 節。

## 3. 地圖風格：背景

### 3.1 背景結構（實測）

```json
{ "bs": "aquaRoad3", "no": 0, "ani": 0, "x": 0, "y": 0,
  "cx": 0, "cy": 0, "rx": -10, "ry": 0,
  "type": 2, "front": 0, "f": 0, "a": 255, "inLayer": false }
```

| 欄位 | 意義 |
|---|---|
| `bs` | 背景 set 名（對應 `Back/*.img`） |
| `no` / `ani` | 影格編號 / 動畫影格 |
| `x` `y` | 放置座標 |
| `rx` `ry` | **捲動偏移**——視差效果的來源 |
| `type` | 背景層級 |
| `front` | 前景（1 = 蓋在角色前面） |
| `a` | 透明度 |
| `inLayer` | 是否綁定圖層 |

### 3.2 背景的兩種來源（對應你的需求 3）

1. **現有地圖的成形背景** → 直接複製 `bs` + `rx/ry` 參數。
   深海峡谷用了 `aquaRoad3`，開往聖地背景多達 27 層——**背景層數是風格的重要指標**。
2. **使用者提供的圖片** → 需要新增圖片進 `Back/*.img` 再引用。

> **實測**：背景層數差異極大（蘑菇村 1 層、新的启程3 32 層、開往聖地 27 層）。
> 這是可量化的風格特徵，生成器應該把它當參數控制。

## 4. 細化：物件與裝飾

### 4.1 物件路徑結構

```
os / l0 / l1 / l2        例：dungeon2 / deepSee / nature / 20
```

DTO 欄位：`os`(前綴) `l0` `l1` `l2` `x` `y` `z`(圖層) `zm`(深度排序) `art`

### 4.2 物件分類（實測分佈）

| 前綴 | 總數 | 出現在 | 意義 |
|---|---:|---|---|
| `dungeon2` | 145 | 2 張 | 洞穴結構（牆、地形塊） |
| `acc9` | 86 | 1 張 | **裝飾** |
| `acc1` | 58 | 1 張 | **裝飾** |
| `connect` | 57 | 3 張 | **連接件 / 前景遮罩** |
| `acc5` | 23 | 1 張 | 裝飾 |
| `acc11` | 21 | 2 張 | 裝飾 |
| `guild` | 15 | 1 張 | 公會建築 |
| `guide` | 3 | 1 張 | 引導 |

**三大類別**（地圖營造的核心）：

```
acc*      裝飾物    → 樹木、燈籠、招牌、石頭、雜物
connect*  連接件    → 前景遮罩、轉場、畫面銜接
dungeon*  結構塊    → 岩壁、洞頂、地形本體
```

### 4.3 `zm` 深度排序

`z` 是圖層、`zm` 是同層內的繪製順序。深海峡谷同一素材 `dungeon2/deepSee/nature/9`
出現 `zm` 1,3,4,5,13,21,32,37 ——**同素材靠 zm 決定前後**。
生成多個同類物件時，`zm` 必須依 y 座標遞增分配，否則會穿插錯誤。

### 4.4 怪物（life）與反應爐

```json
life:    { "id": 8140555, "x": -722, "cy": 302, "fh": 133 }   ← fh 綁定 foothold 編號
reactor: { "id": 2302001, "x": -563, "y": 1128 }
```

**怪物必須綁定 foothold**（`fh` 欄位），不能只給座標——
它靠 foothold 取得高度與重生範圍。

## 5. 地圖重力機制

### 5.1 foothold 結構

```json
{ "id": "1", "layer": "4", "group": 0,
  "x1": -942, "y1": 1829, "x2": -908, "y2": 1834,
  "prev": 0, "next": 2 }
```

### 5.2 三條硬規則（實測驗證）

**規則一：foothold 的 layer 跟著視覺圖層走**

> **這一條是修正後的結論。** 最初只抽到深海峡谷時，以為 foothold 一律在
> layer 4。擴大到 7 張地圖後推翻：

| 地圖 | foothold 總數 | layer 分佈 |
|---|---:|---|
| 深海峡谷2 | 156 | `L4=156` |
| 東部岩山Ⅳ | 145 | `L0=21 L1=70 L2=14 L3=40` |
| 海盜試煉場 | 95 | `L3=8 L5=87` |
| 新的启程3 | 58 | `L3=58` |
| 開往聖地 | 58 | `L2=48 L5=10` |
| 蘑菇村 | 13 | `L1=13` |
| 怪異的回廊 | 9 | `L3=9` |

**規則不是「固定某層」，而是「foothold 必須與它所承載的視覺內容同層」**。
東部岩山橫跨 4 層、深海峡谷只有 1 層，是兩種不同的地形策略：
前者是多層樓台式地形，後者是單一大斜面。

**對生成器的意義**：鋪地面時 foothold 的 layer 必須跟著 tile 層走，
不能寫死。這也是為什麼「先鋪 tile 再自動生 foothold」比分開做更可靠。

**規則二：`prev`/`next` 雙向鏈零斷裂**
深海峡谷 156 條鏈，**斷鏈數 = 0**。鏈是角色的行走路徑，
一條斷掉角色就會卡住。這是硬約束，不是建議。

**規則三：`group` 分段**
深海峡谷：group 0 有 79 條（主地面），其餘 group 2/14/15/27/30/34/35/41
是不同區塊。`group` 用來劃分可獨立移動的區域。

### 5.3 走向統計

| 地圖 | 斜坡 | 牆面 | 平地 | 總數 |
|---|---:|---:|---:|---:|
| 深海峡谷2 | **142** | 14 | 0 | 156 |
| 東部岩山Ⅳ | 81 | 45 | 19 | 145 |
| 海盜試煉場 | 31 | 58 | 6 | 95 |
| 蘑菇村 | 2 | 11 | 0 | 13 |

**斜坡是主流**——這是橫向卷軸地圖的本質：地形是連續的傾斜面，
不是階梯。垂直軸（wall）代表牆、天花板、重力牆。

> **太空／特殊重力場景的機會**：因為 foothold 是**明確的線段＋鏈**，
> 只要能產生符合鏈規則的線段集合，重力方向就能自由定義。
> 反向重力（天花板行走）= 鏈的 y 座標翻轉；磁力牆 = 鏈的 x 座標翻轉。
> **這是現有架構天然支持的，不必重寫。**

## 6. 已知陷阱（生成器必須避開）

### 6.1 ~~API 會給出「有圖但其實是空」的素材~~（**已更正：這個結論是錯的**）

> **2026-10-11 更正。** 本文初版寫「`ancientForest` 是無效素材，
> `sets` 端點說謊」。**這個結論是錯的，原因是我的測試有誤。**
>
> 重新驗證的結果：
>
> ```
> /palette/sets?kind=Tile
>   ancientForest → thumbPath=f1/Tile/ancientForest.img/bsc/0  drawableEntries=18
> /palette/preview?path=.../bsc/0
>   → {"w":90,"h":60,"missing":false,"hasPixels":true}      ← 有真實像素
> /place ... u=bsc no=0  → HTTP 200                          ← 放置成功
> /place ... u=bsc no=10 → HTTP 400
>   "Tile/ancientForest.img/bsc/10 does not resolve in the open session"
> ```
>
> **真相**：`ancientForest` 是完全正常的素材，有 18 個可繪製條目。
> 我當時用 `bsc/10` 測試——那個編號**本來就不存在**。
> 系統的回應不但正確，而且精確指出是哪一個參數不對。
>
> **第二層誤判**：我還把 `/palette/entries` 的 `path` 傳成**地圖路徑**，
> 拿到的是「這張地圖用到的 9 筆」而不是「這個 set 的全部 18 筆」。
> 傳 set 路徑就正常了。**端點一直是好的，是我的參數錯。**
> 速查見第 10 節。
>
> **真正學到的**：API 的錯誤訊息品質很高，**要讀它**。
> 它直接告訴你哪個參數解析不到——而我當時選擇了懷疑 API 而不是懷疑自己。

### 6.2 查詢語意的陷阱（實測確認，**這個是真的**）

| 端點 | 回傳的是 | 常見誤讀 |
|---|---|---|
| `/palette/sets?kind=Tile` | 該 kind 的**所有** set（109 個） | 以為只回地圖用到的 |
| `/palette/entries?kind=Tile&path=...` | **這張地圖**已使用的條目 | 以為是整個 set 的清單 |

`entries` 有 `set` 參數可指定要看哪個 set，**但它沒接**（實測傳了也無效，
回的全部是 9 筆 foothold/portal/life）。要查某個 set 的完整條目，目前只能
用 `/palette/preview?path=<set>/<u>/<no>` 逐點問。

> **對生成器的意義**：想知道 `ancientForest` 有哪些可用編號，
> 現在沒有「列出這個 set 的所有條目」的端點。這是真實缺口。

### 6.3 中文地圖名搜尋失敗

`/maps?q=<中文>` 回 `total: 0`，即使 String.wz 已開啟且名稱存在
（實測 `/maps?limit=10` 能拿到「彩虹岛 : 蘑菇村西入口」等名稱）。
推測是查詢比對未做 Unicode 正規化。**未驗證根因，待查。**

## 7. 給生成器的介面需求（由實測反推）

以下每一項都對應上面觀察到的真實負擔：

| 需求 | 理由（實測依據） |
|---|---|
| `batch` 批量端點 | 鋪一片地面要數百次 place；語意優先於速度（20 次僅 0.17s） |
| `fillFloor(範圍, set)` | 圖層以 `tS` + 平鋪為主（蘑菇村 40 tiles/0 objs） |
| `buildTerrain(輪廓)` | 斜坡是主流（142/156），需要能生成連續斜面 |
| `connectFootholds()` | 鏈零斷裂是硬約束，必須有工具驗證與修復 |
| `link` 追蹤 | 3/10 是 stub，不追蹤會生成空殼 |
| `scatterDecor(prefix)` | acc* 是裝飾主體 |
| `assignDepthOrder()` | `zm` 決定同素材前後 |
| `validate()` | 檢查素材真實存在、鏈完整、怪物有 foothold |
| 範本抽取 | 尺寸型態/層配置/tile set 組合可直接從現有地圖學 |

## 9. `auto-foothold` 在實際素材上是空的（實測）

`/auto-foothold` 從素材自帶的 foothold 幾何生成鏈條
（`Tile/<set>.img/<u>/<no>/foothold` 是 Convex 點集）。

**實測結果：沒有任何素材帶這個幾何。**

```
掃描 25 個 Tile set → 帶 foothold 幾何的：0
ancientForest 18 個條目 → hasFoothold 全部 False
掃描前 12 個 Obj set → 帶 foothold 幾何的：0
```

呼叫時的回應：

```
"Tile/ancientForest.img/bsc/0 carries no foothold geometry of its own, so there
 is nothing to generate from. Draw the chain by hand instead — generating a guess
 here would be exactly the silent invention this tool refuses."
```

> **這句拒絕訊息是本專案最好的設計**：寧可什麼都不做，也不猜。
>
> **對生成器的意義**：鋪地面之後**必須自己算 foothold**，
> `auto-foothold` 幫不上忙。這是 P1-2 場景生成的主要工作量。

## 10. 查詢語意速查（實測確認，踩過的坑）

| 端點 | `path` 參數要傳什麼 | 回傳 |
|---|---|---|
| `/palette/sets?kind=K` | 不需要 | 該 kind 的**所有** set（Tile 109 / Obj 112） |
| `/palette/entries?kind=K&path=P` | **set 路徑**（`f1/Tile/ancientForest.img`） | **那個 set** 的所有條目，含 `hasFoothold` |
| `/palette/entries?kind=K&path=P` | 傳地圖路徑 | 只回**該地圖用到的**條目 |

> **我踩過這個坑**：先傳地圖路徑，得到 9 筆 foothold/portal/life，
> 誤以為 `ancientForest` 沒有視覺素材。傳對參數後是 18 筆 90×60 的圖塊。
> **端點一直都能用，是參數傳錯。**
