# go-01 — 一次收掉技能鏈的所有缺口

開於 2026-10-18。上一輪（W-084/085/086/087）的結果：gate 紅 0，66 個可施放技能 64 個造成傷害。

## 為什麼有這一輪

W-087 揭示的不是「22 個技能壞掉」，而是**一條共用量測路徑跑 66 種資料形狀會壞**。那意味著還沒被量到的形狀很可能也壞，只是還沒被問到。

這一輪的規則：**每一條缺口都要有一個具體的、可跑的檢查；沒有檢查的「修好了」不算數。**

## 缺口清單

### A — 傷害與命中框

- **A1** 5101002 回马：plan 讀到 `damage: 88`，框 `0,-50 .. 140,0`，怪在 32px（框內）正前方，左右兩個朝向都不中。`LevelKeys` 證明讀取器無關。是命中框映射。
- **A2** `mobCount > 1` 從未被真的驗過。計畫是「依距離排序取 N 個」，但 66 技能掃描全程只有一隻怪在範圍內。`mobCount` 分佈 1/2/3/4/5/6/12/15/30，**每個 N 值都要驗一次選取正確**。
- **A3** `hRange = 1.5`（只有 4121008 忍者衝擊）。倍率實際作用於哪一條邊，參考怎麼算。
- **A4** `damageWaitTime`（15/25/47/70/112 都有）。計畫裡傷害是落在施放那一幀還是時間軸事件上？W-087 的掃描讀施放後一幀的 HP，64 個都掉 100 —— 但 `damageWaitTime: 70` 的技能不應該那麼快。
- **A5** `collisionCount` 與 `mobCount` 並存且數值不同（例：2121007 mob 15 / coll 15，5211004 mob 2 / coll 2，5101004 mob 3 / coll 3）。看起來相同，但沒人確認過。

### B — 視覺

- **B1** 逐幀落位目前只有 **1121008** 走過判官。判斷依據應該是**形狀**不是 id：依 `fxFrames`（1..26）× `fx`（1..5 張）分組，每組挑一個代表跑逐幀比對。
- **B2** `fx` 最多 5 張（W-076 的 z 排序）。66 技能掃描只確認 `skillEffects.length > 0`，沒確認 5 張都畫且順序正確。
- **B3** `actions` 有 1 張也有 2 張。兩張的技能畫了幾張？
- **B4** 地面貼花的 fallback 分支（`SkillUseEffect.cpp:263-266`，框內沒有 foothold 時貼在施法者腳下）從未執行過。浮空圖 / 框落在兩層樓梯之間會走到。
- **B5** MultiStrike 多次命中時，怪身上的命中特效會不會疊成一團。

### C — 機制語意

- **C1** `MultiStrike` 在 W-083 移除傷害守衛之後，**它現在還代表什麼**？參考 `Skill.cs` 裡它是什麼意思？我們讀對了嗎，還是它現在只是一個無人消費的旗標？
- **C2** `pos` 1–4：已知 `Mob::show_effect` 只有 `case 0` 有位移（頭），1–4 是空實作。命中特效目前送 `pos: 0`。參考有沒有非 0 的用法？
- **C3** `levelKeys` 已經證明讀取器看得到的樹和 `/api/children` 一致（改壞那次是 bug 不是架構問題）。但 `SkillCastService` 還有沒有第二個只認單一節點名的讀取器？`effectDistance`、`mobCount`、`range`、`maxLevel` 都逐一確認。

### D — 對標稽核（唯讀）

- **D1** `MapleBench/Services/Simulate/*.cs` 與 `walkview.js` 裡每一條 `Xxx.cpp:NN-MM` 引用，逐條核對：檔案存在、該行確實講的是註解裡說的那件事。`pm/PARITY.md` 明訂衝突時 C++ 勝。
- **D2** 產出一份清單：引用正確 / 行號偏移 / 講錯 / 指向不存在檔案。

### E — 驗證工具

- **E1** 把 W-087 的 66 技能形狀掃描變成常駐 gate suite（`%LOCALAPPDATA%/hermes/cache/scratch/`），這樣「今天 64 個」不會變成「明天不知道幾個」。
- **E2** gate 在負載下會紅、單獨跑會綠：`knockback` 已經確認是這麼回事。**`ball-art` 不是**（MEASURED 2026-10-22：它的紅綠由「怪發哪一招」與球的 ~130 ms 飛行窗口決定，不是負載 —— 該 suite 的斷言原本只抽一個樣本，2026-10-22 已改為對全體觀測計數）。找出是什麼時間條件，並讓 suite 自己報告時序，而不是靠人看出聲。
