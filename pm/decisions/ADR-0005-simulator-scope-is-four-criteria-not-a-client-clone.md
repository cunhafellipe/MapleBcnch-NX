# ADR-0005 — 模擬器的驗收標準是四條，不是複製客戶端

> 2026-10-17 02:40。使用者陳述，屬於專案層級的範圍決定，往後每一次「要不要更像客戶端」的
> 爭議都以這份為準。

---

## 決定

**MapleBench 的模擬器不是遊戲，是測試工具。它的任務是「測試效果」，驗收只有四條：**

1. **位置準確** — 畫在哪裡就是封存／參照算出來的位置
2. **機制準確** — 施放的因果鏈成立（按鍵 → 姿勢 → 傷害 → 特效）
3. **有即時效果** — 用封存自己的時間軸與速率播放，不是編造的常數
4. **正常可見** — 使用者看得到、看得出對不對

**不要求、也不做：** 把客戶端一比一複製。冷卻時間、MP／HP 消耗、技能等級門檻、
武器需求、完整的效果節點種類、命中特效與地面貼圖、投射物彈道——
這些是**遊戲規則**，不是**測試工具的驗收條件**。

---

## 為什麼

2026-10-16 晚間我做了一次 C++ 客戶端與模擬器的完整比對（`pm/work/` 兩份 SEG 日誌 +
`Skill.cpp` / `SkillUseEffect.cpp` / `Player.cpp` / `SkillData.cpp` 的逐行比對），
列出十項差異。其中「冷卻時間不存在」「MP 不扣」「沒有技能等級門檻」三項在
**測試工具的用途下完全無害**——測試者要的是按下去能看到位置對、機制通、
特效即時，而不是被冷卻擋住不能連續測。

`pm/W-017` 早已記錄 MP 不扣是使用者的決定。這份 ADR 把同一個原則推廣到其餘幾項：
**凡是只影響「玩起來像不像遊戲」、不影響「測試結果可不可讀」的規則，一律不做。**

---

## 這條規則怎麼用

| 情況 | 做法 |
|---|---|
| 缺陷讓畫面位置、因果鏈、時間軸、可見性出錯 | **修**。這就是四條。 |
| 差異只是「遊戲規則比較完整」（冷卻、MP、等級、武器、道具消耗） | **不修**，也不開工作項目。 |
| 差異是「讀封存的方式不同於參照」且會讓顯示錯 | **修**。位置準確與即時效果都在四條裡。 |

判準一句話：**它會不會讓測試者看錯結果？會，就修；不會，放著。**

---

## 明確不做的事（避免下次又走進去）

- 不實作冷卻時間、不實作 MP/HP 消耗、不實作技能等級門檻、不實作武器需求
- 不把效果的節點種類補齊到與 C++ 一致（`CharLevel` / `prepare` / `affected` /
  `special` / `tile`），除非它讓某個技能**完全看不到**
- 不追求像素級一致，只要求「位置對、機制通、及時、可見」

---

## 與既有規則的關係

`pm/PARITY.md` 說「C++ 為權威，衝突時以 C++ 為準」。
**本 ADR 不牴觸那條——它限定的是「範圍」，不是「正確性」。**
範圍內的事仍然以 C++ 為權威；範圍外的事根本不做。

這一點在 2026-10-17 凌晨已經實際發生過一次：我讀了 C# 工具的 `Skill.cs:397-406`
（`origin.X - ImageWidth`）去實作鏡射，而客戶端的 `DrawArgument.h:143-156` 是
`xscale * (pos - origin)`。**兩者不一致，而 C++ 才是對的。**
「以參照為準」沒有錯過一次——錯的是我先讀了工具。
