```

        ↓
第 2 波 ── 文件與紀錄的一致性（成本低、可平行、風險低）＋ 已在進行中的效能工作
```

## 二、每一張卡怎麼走完（流程固定，不要跳步）

```
0. 量前提 ── 先量前提是否成立，不要照抄卡片
             （今晚兩次證明：前提可能是假的、也可能已經過期）
1. 開卡 ── 寫入範圍互斥（同一時間同一檔案只能有一張卡）
          描述裡必備：絕對路徑、已知陷阱、驗收條件、產出檔名
2. maker 交 ── 只改被指派的檔案；不簽自己的收工
          報告：ASCII、無 BOM、LF、有尾端換行、附上每一條指令與輸出
3. checker 覆核 ── 不同的人、唯讀、**推翻式**（不是確認式）
          每條主張逐字引用，然後 UPHELD / REFUTED / UNTESTED
4. lead 覆驗 ── 自己跑，不看別人的結論
          ★ 「建置成功」不等於「修好了」
5. commit ── 只 stage 自己的檔案（★ 禁止 git add -A：別人的並行改動會被掃進來）
6. 閘門重跑 ── 對著**由新樹建出來的 instance**（rule 17）
          產出：GATE_SUITES_RAN / RED SUITES / GATE_EXIT / GATE_INSTANCE_STALE
7. 推 GitHub ── 確認 behind/ahead = 0/0
8. 更新紀錄 ── pm/OPEN-PROBLEMS.md 與 pm/work/W-104 的狀態
9. 交叉檢查 ── 每一條宣稱都有產物落盤（digest 或檔案），沒有就記成「未驗證」
```

**每張卡的驗收必須自帶「會翻轉的臂」**：一個只會回綠的檢查不是檢查。
今晚用過的兩種形狀，繼續沿用：

- **正向控制臂**：故意做壞它（刪掉快取檔／把擺放推到邊界／餵一個不一致的 census），
  檢查必須變紅。
- **負向控制臂**：一個假訊號（例如 `error` 而非 `BAD=`）必須讓檢查維持綠。

## 六、這一輪不要做的事（寫下來免得重蹈）

- 不要在別人正在改的檔案上開第二張卡（今晚 `NxWriter.cs` 同時掛了 task-18 與 task-69）。
- 不要用 `git add -A`（今晚掃進過別人的並行改動）。
- 不要在 `.ps1` 裡內嵌 repo 路徑（路徑含非 ASCII，PS 5.1 用 ANSI 讀會變亂碼；今晚連踩兩次）。
- 不要把「卡片的前提」當成「已量過的事實」——今晚有兩張卡的前提分別被**推翻**（task-73）與**過期**（W-094）。
- 不要讓 maker 自己簽收工。
- 不要在閘門跑完之前 commit（會和跑中的閘門互相干擾：閘門讀的是檔案，不是 commit）。
