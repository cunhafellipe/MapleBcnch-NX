## 二、🔴 重寫 CharacterPhysics：模型錯了，不是 bug

前一輪的診斷是「`FindBelow` 有缺陷」。**那是錯的診斷。**

`FindBelow` 沒有缺陷。**用它的那個模型才有缺陷。**

詳見 [2026-10-11-physics-blocked.md](2026-10-11-physics-blocked.md)：
六次修正、每次都改善數字、沒有一次解決問題。

### MapleNecrocer 實際怎麼做

讀了 `MapleCharacter.DoMove`（第 519 行起）之後：

```csharp
// 角色持有「當前 foothold」FH，不每步去查地面
Direction = GetAngle256(X2, Y2, X1, Y1);
X += (float)(Sin256(Direction) * SpeedL);
Y -= (float)(Cos256(Direction) * SpeedL);      // 沿 foothold 方向走

// 走到端點才切換
if ((X <= FH.X1) && (FH.PrevID != 0) && (!FH.IsWall()) && (!FH.Prev.IsWall()))
{
    FH = FH.Prev;
    X = FH.X2;
    Y = FH.Y2;
}
```

| | MapleNecrocer | 我寫的 |
|---|---|---|
| 狀態 | 當前 foothold `FH` | `(x, y)` + 每步查詢 |
| 移動 | 沿 foothold 角度 | 先橫移，再查地面 |
| 換 foothold | 走到端點時 | 每步重新查詢 |
| 斜坡 | **自動正確** | 不穩（表面每 px 都不同） |
| 需要 FindBelow | 只有落地/梯子離開時 | 每一步 |

**角色從來沒有「腳下有沒有地面」這個問題**，因為它站在 foothold 上。
這就是為什麼我修 `FindBelow` 永遠修不好。

### 重寫的形狀

```
每一步：
  1. 沿 FH 的角度移動  X += sin(θ)*speed,  Y -= cos(θ)*speed
  2. 越過端點 → FH = FH.Next, 位置設為新端點
  3. 沒有下一段 → 鏈的盡頭，回報
```

`FindBelow` 退回只在**跳躍與梯子離開 foothold** 時使用。

## 三、動手前必須先確認的三件事

### 1. 步行速度的真實值

我用的 `Acceleration 0.2` / `MaxWalkSpeed 4` 來自 scout 報告的
`JumperSprite` **預設值**（`SpriteEngine.cs:1519-1523`）。
但 `Player.DoMove` 裡是：

```csharp
SpeedL += 1.5f;   if (SpeedL > 2.5f) SpeedL = 2.5f;   // 左
SpeedL -= 0.25f;  if (SpeedL < 0)    SpeedL = 0;       // 鬆手減速
```

**差了一個數量級。** `Player` 覆寫的只有跳躍三個
（`JumpSpeed 0.6` / `JumpHeight 9.5` / `MaxFallSpeed 8`，
`MapleCharacter.cs:136-138`），步行速度走的是自己的常數。

**以 `DoMove` 的原始碼為準，不要用 scout 摘出的預設值。**

### 2. 角度要不要離散化

`GetAngle256` + `Sin256`/`Cos256` 是 256 分度查表
（`PIConv256 = -40.743665431f`，`SpriteEngine.cs:749,774-781`）。

本專案若直接用浮點斜率，視覺誤差應 < 1px。
**先確認有沒有實際差異再決定要不要照抄**——多一層查表是額外的複雜度。

### 3. 座標與偏移

`Y -= cos(...)` 表示 Y 向下為正，與本專案一致 ✓。
但 `Player.Offset.Y = -79`、`Offset.X = -40`（第 118-119 行）
是渲染用的錨點偏移，**要分清楚哪些是物理、哪些只是畫圖**。

## 六、選 B 的話：完整分解

以下是依 MapleNecrocer 的實作與本專案的現況推導，**尚未實作**。

### 階段 1：角色物理（無渲染）

```
FootholdPhysics 擴充
  ├─ FindBelow(x, y)          已有，驗證過
  ├─ 表面法向量                斜坡的行走方向
  └─ 碰撞判定                  角色體型 vs 牆面

CharacterMotion（新增）
  ├─ position, velocity
  ├─ walk / jump / fall
  ├─ 重力常數                  必須查證，不可用猜的
  └─ step(dt) → 新狀態
```

**必須遵守的實測規則**（全部來自 `docs/MAP-STRUCTURE.md` 第 5 節）：

1. **foothold 的 layer 跟著視覺圖層走**，不是固定值
   （東部岩山 `L0=21 L1=70 L2=14 L3=40`）
2. **`prev`/`next` 雙向鏈零斷裂**。實測所有既有地圖斷鏈數都是 0
3. **斜坡是主流**（深海峽谷 142/156 斜坡，東部岩山 81/145）

**驗收**：agent 生成地圖 → 模擬角色走全程 → 報「第 N 個 foothold 走不過去」
→ agent 修 → 重跑。這條閉環是終極目標。

### 階段 2：逐幀迴圈 + 怪物 AI

```
WorldSim（新增）
  ├─ entities[]                角色、怪物、NPC
  ├─ tick(dt)                  固定時間步長
  └─ 事件佇列                  傷害、死亡、生成

MobAI（新增）
  ├─ 巡邏路徑                  怪物是否沿自己的 foothold 移動
  ├─ 仇恨與攻擊範圍
  └─ 刷新與重生
```

**這階段風險最高。** 怪物 AI 的細節必須從真實客戶端觀察，
不能憑空設計。MapleNecrocer 的 `Mob.cs` 可參考，但它的實作是
static 全域架構，需要重新設計。

### 階段 3：視覺呈現

**這階段要小心不要重寫已有的東西。** 本專案已有 2,224 行的
canvas 渲染器，怪物 sprite 也能從 Mob.nx 正確產出路徑。

要做的是**新增**：
- 一個角色 sprite 的繪製（讀 Character.wz）
- 逐幀播放動畫
- 讓既有的怪物繪製接上模擬狀態

**不是**重寫渲染器。

## 十、給下一個接手的人的警告

**不要去修 `FindBelow`。** 它是正確的查詢。
看到「角色穿過斜坡」時，正確的反應不是給查詢加容差，
而是問「角色的移動模型對不對」。

前一輪加了 `reach`、`LandingTolerance`、`Math.Ceiling`、
`SurfaceAtExact` 四層容差，沒有一個是對的——
它們全部是在掩蓋「每步查詢」這個模型本身的問題。

**動手前先讀 `MapleCharacter.DoMove` 第 519 行起。** 那裡有答案。
