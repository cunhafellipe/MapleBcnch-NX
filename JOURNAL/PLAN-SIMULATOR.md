# PLAN — 模擬器：從可達性檢查到模擬遊戲環境

寫於 2026-10-11 · 前置：[2026-10-11-simulator.md](2026-10-11-simulator.md)

---

## 現在的真實狀態

`/api/simulate/walk` 能沿 foothold 的 `next` 鏈走，回報走了幾段、
涵蓋多少寬度、卡在哪。150 張真實地圖零錯誤。

**但它不是模擬器。** 它不模擬角色，不模擬重力，不跑逐幀迴圈，
不會讓怪物做任何事。MapleNecrocer 的 14 項做了 2 項。

而且它抓不出 `/validate` 抓不到的東西——那才是它本該提供價值的地方。

---

## 一、先決定：這條路要走嗎

三個選項，會導向完全不同的下一輪。

### A. 放棄模擬器，只保留可達性檢查

把頁面與說明誠實改名為「可達性檢查」，說明它只查鏈。

- 成本：近乎零，現有程式幾乎不用動
- 代價：`WalkResult.Path` 之類為視覺化準備的東西要重新評估
- 適用：認為「地圖能走」這件事，`/validate` 已經夠了

**我的看法**：如果選 A，`/validate` 加上這個端點確實重疊度很高。
真要留，它得先證明自己比 `/validate` 多做了什麼。

### B. 補完真正的模擬 ⬅️ 使用者的原始需求

角色物理、怪物 AI、逐幀迴圈。這才是 MapleNecrocer 的量級。

- 成本：大。見下面第三節的分解
- 代價：會碰到渲染層，而渲染層已存在且不該重寫
- 適用：使用者要的是「模擬遊戲環境」

### C. 只做「能不能玩」的驗證，不做視覺模擬

不畫角色、不跑動畫，只用物理規則驗證地圖：
放一個角色在起點，模擬輸入左右移動，看能不能走到終點、
會不會卡住、會不會掉出地圖。

- 成本：中
- 代價：玩家看不到，但 agent 得到可驗證的答案
- 適用：目標是「讓 agent 產出的地圖真的能玩」，不是「做個遊戲」

**我傾向 C 再走向 B。** 先讓物理正確可驗證，再視覺化。
反過來做會得到一個好看但不知道對不對的東西。

## 二、無論選哪條，先修的三件事

### 1. 它抓不出斷點 🔴

實測：同一張地圖 `startX=0` 只走 2 段就到 53%，但回報
`walkable: true, conclusive: false`。**它不會說「這裡有斷點」。**

`/validate` 能抓斷鏈，但它抓不到「鏈完整卻中途到不了邊」。
這才是它該證明價值的地方，目前沒證明。

**要做的**：回報裡明確區分「鏈在此結束」與「鏈在此斷掉」，
並指出斷在哪個 foothold id。

### 2. 判定語意要重新定義

現在的 `walkable` 是「沒被東西擋住」，容易被讀成「地圖完整可通行」。
實測 150 張裡 40 張是 `walkable_partial`——這些都被標成 true。

**要做的**：三態取代二態：
- `complete` — 走到全圖右緣
- `partial` — 鏈完整但只覆蓋部分（多層地圖的正常情況）
- `broken` — 鏈在中途斷掉
- `stub` — link stub，幾何在別處

### 3. 起點選法要明確

現在是「往右掃找第一個可站的點」，這個啟發式在真實資料上
修過兩次（牆角、垂直牆），但沒有保證。

**要做的**：讓呼叫端明確指定起點，或明確宣告「從最左可站立點開始」，
不要在背後猜。

## 三、選 B 的話：分解與順序

以下是依 MapleNecrocer 的實作與本專案的現況推導，**尚未實作**。

### 階段 1：角色物理（無渲染）

```
FootholdPhysics 擴充
  ├─ FindBelow(x, y)          已有，驗證過
  ├─ 表面法向量                斜坡的行走方向
  └─ 碰撞判定                  角色體型 vs 牆面

CharacterMotion（新增）
  ├─ position, velocity
  ├─ walk / jump / fall
  ├─ 重力常數                  必須查證，不可用猜的
  └─ step(dt) → 新狀態
```

**必須遵守的實測規則**（全部來自 `docs/MAP-STRUCTURE.md` 第 5 節）：

1. **foothold 的 layer 跟著視覺圖層走**，不是固定值
   （東部岩山 `L0=21 L1=70 L2=14 L3=40`）
2. **`prev`/`next` 雙向鏈零斷裂**。實測所有既有地圖斷鏈數都是 0
3. **斜坡是主流**（深海峽谷 142/156 斜坡，東部岩山 81/145）

**驗收**：agent 生成地圖 → 模擬角色走全程 → 報「第 N 個 foothold 走不過去」
→ agent 修 → 重跑。這條閉環是終極目標。

### 階段 2：逐幀迴圈 + 怪物 AI

```
WorldSim（新增）
  ├─ entities[]                角色、怪物、NPC
  ├─ tick(dt)                  固定時間步長
  └─ 事件佇列                  傷害、死亡、生成

MobAI（新增）
  ├─ 巡邏路徑                  怪物是否沿自己的 foothold 移動
  ├─ 仇恨與攻擊範圍
  └─ 刷新與重生
```

**這階段風險最高。** 怪物 AI 的細節必須從真實客戶端觀察，
不能憑空設計。MapleNecrocer 的 `Mob.cs` 可參考，但它的實作是
static 全域架構，需要重新設計。

### 階段 3：視覺呈現

**這階段要小心不要重寫已有的東西。** 本專案已有 2,224 行的
canvas 渲染器，怪物 sprite 也能從 Mob.nx 正確產出路徑。

要做的是**新增**：
- 一個角色 sprite 的繪製（讀 Character.wz）
- 逐幀播放動畫
- 讓既有的怪物繪製接上模擬狀態

**不是**重寫渲染器。

## 四、怎麼驗證才算數

前一輪的教訓（見日誌第七節）：實測通過不等於達到標準。

所以這一輪的驗收條件必須先寫死：

| 層次 | 驗收 | 怎麼證明 |
|---|---|---|
| 物理 | 角色能走過**真實遊戲地圖** | 在 20 張已發布地圖上模擬，結果與人工走過的一致 |
| 物理 | 能抓出 `/validate` 抓不到的問題 | 刻意做一張鏈完整但有洞的地圖，模擬必須報錯 |
| AI | 怪物行為合理 | 在有怪物的地圖上跑，怪物不穿牆、不浮空、不卡住 |
| 視覺 | 看得到角色與怪物 | 截圖 + 讀 canvas 像素確認非空白 |

**「沒有怪物會動」不能算通過。** 前一輪就是這樣差點交付。

## 六、建議的下一輪順序

1. **先回答第一節的 A/B/C。** 這決定後面全部工作，猜錯就全部白做
2. 修第二節的三件事（判定語意、斷點回報、起點選法）——不管選哪條都要做
