## 一、客戶端在解決什麼問題

### 1.1 它面對的問題

客戶端要回答的是：**一個 2D 角色站在一張由數百條線段組成的地圖上，每幀 60Hz 被玩家用鍵盤推動，怎麼決定它下一幀在哪裡？**

這個問題的困難不在物理，而在**地圖不是一個連續平面**：

- foothold 是離散的線段，彼此用 `prev`/`next` 串成鏈
- 鏈與鏈之間**不連通**（有高差、有牆、有空隙）
- 同一張地圖有多層（`Z` = layer 索引），視覺上重疊但物理上獨立

所以「角色在哪裡」不是一個座標，而是**「在哪一段 foothold 上，朝哪個方向」**。

### 1.2 它的三個設計決定

#### 決定 A：**攜帶 foothold 物件，而不是記錄座標**

```csharp
// MapleCharacter.cs:527-530
int X1 = FH.X1;  int Y1 = FH.Y1;  int X2 = FH.X2;  int Y2 = FH.Y2;
```

`DoMove` 開頭就把當前 foothold 的四個座標**快照**出來，
整個函式都只用這四個快照，不重新查詢。

**為什麼**：每幀只做一次狀態判斷，之後所有運算都是純算術。
這讓「角色站在哪裡」變成一個**在函式內不變的量**，
消除了整類 bug——不可能出現「算到一半座標變了」。

#### 決定 B：**移動是沿 foothold 的方向，不是「往目標點走」**

```csharp
// :786-790
Direction = GetAngle256(X2, Y2, X1, Y1);      // 向左走：方向反過來
if (!FH.IsWall())
{
    X += (float)(Sin256(Direction) * SpeedL);
    Y -= (float)(Cos256(Direction) * SpeedL);
}
```

斜坡不是「先水平移動再修正 Y」，而是**沿著那一段線段的真實角度移動**。

**為什麼**：一行算式處理所有地形。水平、斜坡、階梯邊緣是同一個公式的特例。

#### 決定 C：**離開鏈與離開地圖是兩個獨立的判斷**

```csharp
FallEdge = -999999;              // 預設：永不離開
if (FH.Prev == null)             // 只有鏈的末端
    FallEdge = FH.X1 - 10;
if ((JumpState == jsNone) && (X < FallEdge))
    JumpState = jsFalling;
```

**預設值是「不離開」**，只有走到鏈的末端才設成真實邊界，而且還要**再往前 10px**。

**為什麼**：這是整份程式碼最容易被誤讀的一行。
`-999999` 是一個**意圖宣告**，不是一個座標：
「除非確定已經走到鏈的末端，否則絕不離開地面。」

我讀到這裡時把它寫成 `_x <= fh.X1`——**我保留了形狀，丟掉了意圖。**

### 1.3 客戶端的三個特徵，讓它能做到

| 特徵 | 影響 |
|---|---|
| **整個狀態機在一個函式裡** | 沒有「我該呼叫哪個方法」的問題，順序就是語意 |
| **每幀重新求值所有條件** | 沒有累積的狀態需要維護 |
| **輸入直接驅動** | 不需要處理「腳本該按什麼鍵」 |

## 二、我為什麼做不到——三個結構性原因

### 原因 1：我的介面把它拆開了

```csharp
// 我的
public void Step(int moveLeft, int climb = 0)
{
    if (climb != 0 && ...) { ClimbOn(...); return; }   // 梯子優先
    if (!OnGround) { Fall(); return; }
    Walk(moveLeft, out bool leftGround);
}
```

**這個結構在表達一個客戶端沒有的主張：「梯子優先於行走，空氣中優先於行走」。**

客戶端沒有這種主張。它的順序是：**每一幀依序檢查所有條件**，
梯子、空氣、行走**不是互斥的分支，而是同一幀裡並存的規則**。

最直接的證據：`Fall()` 原本只改 Y，因為我把「下落」當成了一個獨立狀態。
客戶端的下落**永遠和行走同時發生**——`:839` 的行走區塊沒有 `JumpState` 判斷，
所以角色走下懸崖時 X 仍在推進。

**我的拆法製造了客戶端沒有的狀態機，然後在這個錯誤狀態機裡找 bug。**

### 原因 2：我把「意圖」當成「形狀」

| 客戶端寫法 | 我的讀法 | 實際意圖 |
|---|---|---|
| `FallEdge = -999999` | 「邊界值」 | **「預設不離開」** |
| `if ((X <= FH.X1) && ...)` | 「交接條件」 | **「走過這一段的近端就換下一段」** |
| `if (!FH.IsWall())` | 「牆上不動」 | **「牆沒有可走的方向」（而 `FH` 永遠不可能是牆，所以是死碼）** |

**三次都是保留了形狀、丟掉了意圖。**

尤其第三個：`FH.IsWall()` 永遠為假，因為 `FindBelow` 的兩個分支都 `continue` 掉 `X1==X2`。
**客戶端自己知道這是死碼**（它留著沒刪），而我「修正」了它——讓角色真的掉下去。

### 原因 3：我把量測當成證據

```csharp
// 我寫的註解
/// measured, a ladder at x=1274 and a foothold ending at x=1256 left the
/// character 18px away, outside the client's box
private const int ClimbReachX = 40;   // 客戶端是 10
```

**那段量測是真的，結論是錯的。**

量測觀察到「角色停在離梯子 18px 處」這個**症狀**，
我沒有去問「為什麼它會停在那裡」——答案是我的 `Fall()` 不做水平位移。

**根因是我少寫了一段程式碼，而我用一個放寬的常數把它蓋住了。**

## 三、那麼「照抄」能不能達成相同效果——逐項分析

使用者問的是這個。答案是：**取決於什麼叫做「照抄」。**

### 3.1 物理段的可照抄程度

```
客戶端物理段（DoMove 的 541-593, 715-744, 774-821, 826-873, 874-916）= 289 行

外部依賴實測：
  Keyboard.*   8 處
  Sound / Animation / Sprite  0 處
```

**289 行裡只有 8 個外部呼叫，全部是 `Keyboard.KeyDown`。**

這 8 處的形態：

```csharp
Keyboard.KeyDown(Input.Left)    →  moveLeft != 0
Keyboard.KeyDown(Input.Up)      →  climb < 0
Keyboard.KeyDown(Input.Down)    →  climb > 0
Keyboard.KeyDown(Input.LeftAlt) →  jump / dropThrough 開關
```

**這是機械式替換，不是設計改變。**8 處替換完畢，281 行完全不動。

### 3.2 照抄能解決什麼

| 問題 | 照抄能否解決 | 原因 |
|---|---|---|
| 交接條件 | ✅ | 位置判斷直接抄進來 |
| 下落的水平位移 | ✅ | 行走區塊與下落並存的結構直接抄進來 |
| 牆探測點 Y-4 | ✅ | 抄進來 |
| 牆的 Z 來源 | ✅ | `FindBelow(X+10, Y-5)` 抄進來 |
| 右向 EdgeSlack +5 | ✅ | 抄進來 |
| 地圖邊界夾制 | ✅ | `Map.Left + 20` 抄進來 |
| `FallMargin = 400` | ✅ | 抄進來就沒有這個東西了 |
| 梯子 `OffY = -3` | ✅ | 抄進來 |
| 梯子底部瞬移 | ✅ | 抄進來 |

**九項全部會消失。**

### 3.3 照抄不能解決什麼

| 問題 | 為什麼 |
|---|---|
| 出生點缺 portal 維度 | `:163-178` 在 `DoMove` **之外**，要另外處理 |
| 怪物 MoveType | 需要 Mob 封存，地圖檔沒有資訊（已窮舉所有 life 欄位） |
| Fly 型怪物 | 需要 `FlySpeed` / `CosY`，同樣在封存裡 |
| 傳送門 type 10 同圖跳 | 在 `:613-629`，不在物理段內 |
| `FallFlag` / 天花板探測 | **客戶端死碼，不該抄** |

### 3.4 照抄的真正風險

**不是「抄錯」，是「抄完後又忍不住改」。**

我這四輪每次修 bug 的方式都是「讀客戶端 → 理解 → 改我的版本」。
這個動作本身會持續產生偏離。

**照抄之後要立一條禁令：沒有量測證明與客戶端不同，就不准動。**

## 四、真正的差距在哪一層

這份分析最重要的結論：

```
我在「實作層」操作（改程式碼）
客戶端的價值在「設計層」（一個函式裡的順序與意圖）
```

**中間缺了一層：把客戶端的設計意圖，提煉成可驗證的規則。**

具體說，我缺少這樣的東西：

```
規則：角色在鏈中間時，永遠不會離開地面
證據：FallEdge 預設 -999999，只有 FH.Prev == null 才設真實值
違背的後果：每條鏈最後一幀掉落（我犯了）

```

```
規則：行走區塊沒有 JumpState 判斷，下落時 X 仍在推進
證據：:824 的入口條件與 :839 的守衛都沒有 JumpState
違背的後果：角色離鏈後懸停（我犯了）
狀態：已修正，但修法是自行發明 DriftWhileFalling
```

**這兩條規則我都是「犯錯之後才學到的」，而不是「讀懂之後避免的」。**

## 五、結論與規劃

### 5.1 剩下的問題，分三類

**類別 A — 照抄可以消除（9 項）**
交接條件、下落水平位移、牆探測點、牆 Z 來源、右向 EdgeSlack、
邊界夾制、`FallMargin`、梯子 `OffY`、梯子底部瞬移

**類別 B — 要另外做（3 項）**
出生點（portal + `PY-2` + `jsFalling`）、傳送門 type 10、
**三條驗收規則的自動化實作**（這是最重要的，因為它防止類別 C 重演）

**類別 C — 確認不做（5 項）**
站在牆上靜止、`FallFlag`、天花板探測（以上客戶端死碼）；
Fly 型、MoveType 自動偵測（資料不在地圖檔）

### 5.2 為什麼類別 B 的驗收規則比什麼都重要

**四輪以來每一次嚴重 bug，測試都是全綠的。**

```
18,000 幀    →  23/23 通過
跳躍 0.3px   →  23/23 通過
角色卡住不動 →  23/23 通過
```

我驗的一直是「會不會爆」，從來沒驗「**結果對不對**」。

三條規則：

```
6. foothold 序列長度 > 1        —— 抓交接 bug
7. 行進距離 / 地圖寬度 比例      —— 抓卡住不動
8. ticks 分布不集中在極小值      —— 抓「跑完但沒走」
```

**沒有這三條，照抄完之後我會用同樣的方式把它改壞，然後測不出來。**

### 5.3 執行順序（與之前的計畫不同）

```
第 1 步  實作三條驗收規則，先讓它們能抓到現有的已知問題
        —— 在照抄之前，否則無法判斷照抄有沒有改善

第 2 步  照抄物理段 289 行，刪除 Step/Walk/Fall/ClimbOn 四個方法
        —— 8 處 Keyboard 替換為參數，其餘逐行保留
        —— 立禁令：沒有量測證明與客戶端不同，不准動

第 3 步  類別 B 的另外兩項（出生點、傳送門 type 10）

第 4 步  重新做一次差距審計，這次帶著「意圖」而非「形狀」去讀
```

**與之前計畫的差別**：之前是「照清單修」，現在是「先建立能抓到問題的規則，
再一次性換掉會產生問題的那部分」。
