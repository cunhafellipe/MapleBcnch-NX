## 一、直接回答：沒有

我做的不是「詳細檢視參考專案」，是**反向比對差異清單**。

區別：

| 我做的 | 應該做的 |
|---|---|
| 客戶端有這行程式碼，我沒有 → 記一筆 | 這行程式碼**會不會執行**？ |
| 客戶端有這個常數，我沒有 → 記一筆 | 這個常數**會不會生效**？ |
| 客戶端有這個方法，我沒有 → 記一筆 | 這個方法**是死碼嗎**？ |

第二種比對會產生三類假差距：
**死碼當成功能、不可達分支當成規則、語意等價當成缺失。**

## 二、證據：審計報告自己寫了，���還是把那條列進計畫

### 2.1 `FindWallL` —— 審計說它「永遠不成立」

審計的 `files` 欄位原文：

```
FindWallL :153-181 (Y1>=P.Y && Y2<=P.Y — unsatisfiable for typical walls)
ClosePlatform :184-195 (dead code)
```

我在報告 §3.3 也寫了：

```
⚠️ 客戶端的 FindWallL 對一般資料恆為 null —— 我比客戶端「更對」
```

**然後我在 25 項計畫裡，把它當成一個「我該對齊」的項目。**

我自己查證了：

```csharp
// Footholds.cs:153-182
if (F.IsWall() && F.X1 >= P.X && F.Y1 >= P.Y && F.Y2 <= P.Y)
```

牆是 `X1 == X2`，而條件要求 `Y1 >= P.Y >= Y2`。
**牆的 Y1/Y2 是原始值未正規化**（`Footholds.cs:240` 直接 `Iter3.GetInt("y1")`），
所以只有當牆的 `Y1 > Y2` 時這個條件才可能成立。

實測：

```
wall Y1=0   Y2=100 → 滿足條件的 P.Y 有 0 個（永遠不成立）
wall Y1=100 Y2=0   → 滿足條件的 P.Y 有 101 個
```

而我的 `FindWall` 用的是正規化後的 `Y1 > y || Y2 < y` 跳過——
**我的做法對一般資料是正確的**。

**結論：這一項不是差距，是我的實作比客戶端的死碼更好。**
照計畫改過去等於把對的程式碼改成壞的。

### 2.2 `ClosePlatform` —— 審計說是死碼，沒有人提

`Footholds.cs:184-195`。審計標了 `(dead code)`。
這代表客戶端**沒有任何呼叫者**。它不是功能，是歷史殘留。

「客戶端有的我就要有」如果照字面執行，
我應該去實作一個客戶端自己都不用的方法。

## 五、修正後的判準

原判準（寫在 `2026-10-12-0941-client-parity-plan.md`）：

> 每一個數字都要能在客戶端找到出處。
> 找不到出處的，不是「需要一個好預設值」，是「這個東西不該存在」。

**這句話只處理了一個方向。** 補上另一半：

> **每一段客戶端程式碼都要先確認它會執行，再拿來對齊。**
>
> - 死碼 → 不對齊。我的實作比較好就留著，並記錄為何比較好。
> - 不可達分支 → 不對齊，並記錄不可達的理由。
> - 語意等價的寫法差異 → 不對齊，除非有實測證明會產生不同結果。
>
> **「客戶端有的我就要有」的前提是「客戶端在跑」。**
> 客戶端沒在跑的東西，我不需要有。

我順手查了 D3（VR 邊界），發現它比我原本寫的嚴重得多。

    Map.Bottom = Map.Info["VRBottom"] + 15;

## 七、下一輪的順序（改）

原順序 `D → A → B → C → E` 建立在「清單正確」的假設上。
既然清單本身可能有假項目，順序要改：

```
第 0 步：先查「客戶端哪些程式碼是死的」
        —— 對 25 項每一項確認它引用的行號在可達路徑上
        —— 查不到的從計畫移除，不是延後

第 1 步：執行確認為真的項目
```

**先驗證清單，再執行清單。** 我之前跳過了這一步，
因為審計報告看起來很權威、很詳細、還附行號。

詳細不等於正確。**一份帶行號的錯誤清單，比一份沒有行號的清單更危險**——
它讓人相信已經查過了。

## 八、這一輪真正學到的

我花三輪做「對齊客戶端」，每一輪都產出更多項目：
28 → 25 → 將來更多。

**產出越來越多，卻沒有一輪問過：這些項目是真的嗎？**

我把你給的標準「他有的我就要有」理解成一個數量遊戲——
他有多少，我就補多少。

但那個標準的前提是**他在跑的東西對我有意義**。
一個沒人呼叫的方法、一個永遠不成立的分支，
補上去只是讓我的程式碼看起來更像他的程式碼。

**像來源，不等於對。** 這跟「像 Bug 的程式碼」是同一個陷阱的兩面。
