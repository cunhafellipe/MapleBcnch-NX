# 2026-10-12 10:55 — P0：角色走過一段 foothold 就再也不會前進

對象：副本 `MapleBcnch-NX-audit` · 基準 `e28cd3b`
來源：第二位驗證者（`VerifyCharacter`）在核對死碼時發現

**這一項不在 25 項清單裡，而且它比清單上所有項目都嚴重。**

---

## 一、症狀

```
f1/Map/Map6/610030510.img，300 步向右走

修正前：走過的 foothold  = ['177']          ← 只有一段
修正後：走過的 foothold  = ['177','188','198','208']
        最終位置 x = 652
```

角色走過第一段 foothold 之後就停在上面，
後面 299 步全部原地不動。

---

## 二、根因

`CharacterPhysics.Walk()` 的交接被掛在 `reachedEnd` 上：

```csharp
bool reachedEnd = moveLeft >= 0 ? _x > fallEdge : _x < fallEdge;
if (!reachedEnd)
    return;                    // ← 只有鏈尾才會走到下面

// 交接
long nextId = moveLeft >= 0 ? fh.Next : fh.Prev;
...
_foothold = step;
```

`fallEdge` 預設是 `999999f` / `-999999f`，
只有**鏈的末端**（`leadId == 0`）才會被設成真實座標。

**所以鏈中間的每一段 foothold，`reachedEnd` 永遠是 false，
程式碼在交接之前就 return 了。**

### 客戶端怎麼做

```csharp
// MapleCharacter.cs:810（向左）/ :862（向右）
if ((X <= FH.X1) && (FH.PrevID != 0) && (!FH.IsWall()) && (!FH.Prev.IsWall()))
{
    FH = FH.Prev;
    if (JumpState == JumpState.jsNone) { X = FH.X2; Y = FH.Y2; }
}
```

**判斷的是位置**——角色有沒有走過當前 foothold 的近端。
與鏈的邊界無關。

---

## 三、修正

把交接的條件從「是否抵達鏈尾」改成「是否走過當前 foothold 的端點」：

```csharp
bool atEnd = moveLeft >= 0 ? _x >= fh.X2 : _x <= fh.X1;
if (!atEnd)
    return;
```

而「沒有下一段可以接」時，是否算掉出地圖，
改由 `reachedEnd` 判斷——**那才是鏈邊界的意義所在**。

兩者的分工現在是清楚的：

| 變數 | 判斷什麼 | 客戶端對應 |
|---|---|---|
| `atEnd` | 是否該把 foothold 交給下一段 | `:810` / `:862` 的位置判斷 |
| `reachedEnd` | 是否已越過鏈的邊界（FallEdge） | `:793-801` / `:845-852` |

### 分布變化是正確的

| 類別 | 變化 | 原因 |
|---|---|---|
| 鏈盡頭 | 775 → **349** | 角色不再半途卡住，會走完整條鏈 |
| 走進傳送門 | 1150 → **1613** | 走到鏈尾之後才會遇到門，現在走得到 |
| 掉落 | 432 → **1179** | 真正走完整條鏈後才掉出去的，是真的掉落 |
| 抵達邊緣 | 3550 → **2652** | 部分原本誤判為「抵達邊緣」的，是走不完整條鏈 |

**「鏈盡頭」減少 55% 是最有意義的訊號**：
那 426 次原本是「鏈還沒走完就停了」，現在真的走完了。

## 五、這一輪的教訓

### 1. 我的驗證方法有系統性盲點

23/23 通過、10,732 次零錯誤、acceptance 22/23——
**所有測試都綠燈，而角色根本走不動第二段。**

我一直在驗「會不會爆」，從來沒驗「走了多遠」。

**應該有的檢查**：`/trace` 回報的 foothold 序列長度。
一張 2,068px 寬的地圖，角色只走過 1 段 foothold——
這件事本身就不合理，但沒有任何一條測試在看它。

### 2. 這與「假差距」是同一個病

`10:25` 我發現清單裡混著**不該對齊的項目**（死碼、語意等價）。
`10:55` 發現清單裡**漏了最嚴重的項目**。

**兩個方向都沒有系統性防線。**

前者靠逐項驗證可達性，後者靠逐項檢查客戶端的判斷條件——
而後者我做了，卻只用在「客戶端有什麼」上，
沒用在「我的實作對不對」上。

### 3. 誠實的部分

`VerifyCharacter` 的報告明確寫：

> 同時發現 1 個審計完全漏掉、且比全部 6 項都嚴重的 P0 級 bug 在我自己的程式碼裡

它在核對**客戶端死碼**的任務裡，順手發現了我的 bug。
因為它讀的是兩邊的原始碼，不是上一輪的結論。

## 六、下一輪該加的驗收

```
1. /trace 的 foothold 序列長度 > 1（多段鏈的地圖）
2. 角色行進距離 / 地圖寬度 的比例健全性
3. 每張地圖的 ticks 分布（全部集中在極小值 = 有 bug）
```

第 3 條最容易做，也最能抓到這類問題：
**10,732 次裡有大量 walks 只走幾十步，那本身就是訊號。**
