## 2. 任務序列

排序依**依賴關係**，不是依好不好做。每一項都有明確的完成定義。

### 階段 A — 讓現有能力可信（先做，因為後面都建立在它上面）

| # | 任務 | 完成定義 | 依賴 |
|---|---|---|---|
| **A1** | 擴大抽樣到 100 張雙向 | 最大偏差 ≤4px、零錯誤、記錄結果到 JOURNAL | — |
| **A2** | 跳躍路徑驗證 | `Jump()` 與 `DropThrough()` 有測試覆蓋；不改行為只補測試 | A1 |
| **A3** | 補 `acceptance.mjs` | 把 `/character` 納入既有的驗收腳本，不另外造 | A1 |

**為什麼先做 A**：現在的驗收只覆蓋「走」路徑。跳躍與落下梯子的方法存在
但從未被呼叫過，等於未測試程式碼。在它們之上蓋東西會重蹈「未驗證就往上疊」的覆轍。

### 階段 B — 補齊 MapleNecrocer 還缺的部分

| # | 任務 | 完成定義 | 依賴 |
|---|---|---|---|
| **B1** | 梯子／繩索攀爬 | 讀 `LadderRopes.cs`，實作尋找與上下；`/character` 可用 | A2 |

**為什麼不做 B4**：逐幀迴圈是為了讓玩家看動畫。驗證地圖不需要動畫，
而且會引入幀率耦合——物理常數是 per-frame 的，變數步長會讓整組數字失真。

## 4. 執行規則

### 4.1 主目錄怎麼同步

主目錄有其他 agent 在用，**不能直接操作**。三種做法：

| 做法 | 步驟 | 適用 |
|---|---|---|
| **A（建議）** | 全部工作在副本完成 → 停止其他 agent → 在主目錄 `git pull` 或複製分支 | 一般情況 |
| B | 在副本完成並 push 遠端 → 主目錄由使用者手動 pull | 主目錄暫時不能動 |
| C | 維持兩份，各自提交 | 不推薦——已經證明會分歧 |

**同步前必須先確認主目錄的 4 個未提交檔案已被副本取代**（MD5 已驗證相同，
但仍需在同步當下重驗，因為其他 agent 可能又改了）。

### 4.2 每輪只做一件事

前一輪同時改了 `FindBelow`、落地判定、移動順序、容差四個變數，
結果每個都無法單獨歸因，浪費一整輪。

### 4.3 動手前先讀原始碼

`CharacterPhysics` 走錯模型整整一輪，根源是「拿到常數就以為懂了」——
scout 給的 `Acceleration 0.2` 是 `JumperSprite` 預設值，
`Player` 實際用 `+=1.5` / 上限 `2.5`。**拿到摘要不動手，先讀原始碼。**

### 4.4 不做的事要先說

沒有把握時說「這個我不確定」，比做出一個壞掉的版本然後花六輪修便宜。

## 5. 明確不做的事

| 不做 | 理由 |
|---|---|
| 逐幀動畫迴圈 | 驗證地圖不需要；引入幀率耦合會讓 per-frame 常數失真 |
| 重寫渲染器 | 專案已有 2,224 行的 canvas 渲染器，怪物 sprite 也能正確產出 |
| 改 NX 格式或存檔路徑 | 不在目標內，且風險最高（存檔涉及資料損毀） |
| 移植 MapleNecrocer 的 WzLib | 它讀 `.wz` 目錄，我們的核心是 NX (PKG4)，路徑不同 |
| 在主目錄操作 | 有其他 agent 在用 |
