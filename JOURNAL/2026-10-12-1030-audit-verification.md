## 一、最重要的發現：清單漏了一項，而且它最嚴重

### `Fall()` 缺水平位移

```csharp
// MapleCharacter.cs:824 的入口條件
if ((FaceDir == FaceDir.Right) && (SpeedL == 0) && (!InLadder))
// :839-843 實際移動
if (!FH.IsWall())
{
    X += (float)(Sin256(Direction) * SpeedR);
    Y -= (float)(Cos256(Direction) * SpeedR);
}
```

**整個行走區塊沒有任何 `JumpState` 判斷。**
所以角色走下懸崖後，X 會繼續推進直到掉出地圖。

我的 `Fall()`（修之前）**只改 Y，完全不改 X**——
角色離開鏈的那一幀就凍結在半空中。

### 這個 bug 掩蓋了另一個 bug

`ClimbReachX = 40`（客戶端是 ±10）的原始註解：

> 量測到梯子在 x=1274，foothold 結束在 x=1256，距離 18px，
> 超出客戶端的 ±10 盒，所以放寬。

**那個 18px 正是我自己少做的水平位移造成的。**
客戶端在同一個位置不會停在 1256，它會繼續往 1274 移動，
用自己的 ±10 盒就抓到了梯子。

**我用一个放寬值蓋住了一個真正的 bug。**

這是本專案到目前為止最典型的錯誤型態：
把症狀當成因，然後寫一個「量測過的」常數去補償。

### 修正

1. 新增 `DriftWhileFalling()`——下落中依客戶端規則保持水平位移並減速
2. `ClimbReachX` 刪除，`FindLadderForClimb` 回到客戶端的 ±10

實測位移（`f1/Map/Map1/100040001.img` 主動墜落）：

```

step 29  x=-30  y=41  fall
step 30  x=-33  y=41  walk
...
step 38  x=-53  y=40  walk
下落期間 X: -30 → -77   有位移: True
```

### 項目 3 為什麼「不要改」——這是本輪的方法論

審計說「客戶端用原始 Y1/Y2，我用正規化 Min/Max，應該改成客戶端的寫法」。

**驗證結果是不能改**，理由不是「語意看起來一樣」，而是：
客戶端自己在**三處不同的地方**用相反方向比較 Y1 與 Y2：

```
:552   if ((InLadder) && (Y < LadderRope.Y1))    // 往上爬，與 Y1 比
:579   if ((Y > LadderRope.Y2) && (InLadder))     // 往下爬，與 Y2 比
:19    P.Y < L.Y2 + 12 && P.Y > L.Y1 - 12
```

三處都只有在 **Y1 < Y2** 時才成立。
客戶端的程式碼本身證明了資料裡 Y1 < Y2，
所以它的寫法與正規化後的 Min/Max **逐位元相同**。

「實測資料裡哪個值較大」本機無法確認（沒有梯子端點樣本），
但**從客戶端自身的三處比較可以推導出結論**——這比量測更有說服力，
因為量測的是資料，推導的是程式碼的相依條件。

### 項目 4／5 的誠實結論

客戶端從地圖 `life` 讀的**每一個欄位**都查了：

| 欄位 | 能否推斷 MoveType |
|---|---|
| `id` | 不能——只是索引，判斷需要 Mob 封存 |
| `x` / `cy` | 不能——所有型別都站在地面上 |
| `rx0`/`rx1` | **反向線索**：只證明「不是 Move 或 Stand 型」，無法區分 Jump 與 Fly |
| `type` | 不能——分 mob/npc，與運動無關 |
| `fh` | **反向線索**：Fly 型完全不碰 foothold，有 `fh` 反而不是 Fly 型 |

**「無法從地圖檔自動偵測 MoveType」是正確且誠實的結論。**
這不是能力不足，是資訊根本不在地圖檔裡。

Fly 型需要 `FlySpeed` 與 `CosY`，兩者都在 Mob 封存裡。
**猜錯比不做更糟**——所以不實作，enum 保留作文檔化的客戶端事實。

## 五、這一輪真正學到的

**「量測過的常數」是最危險的東西。**

`ClimbReachX = 40` 有一段完整的量測理由、註解裡寫了具體座標
（梯子 1274、foothold 1256、距離 18px）。

**那段量測是真的，結論是錯的。**

因為量測觀察到的是「角色停在離梯子 18px 處」這個**症狀**，
我沒有去問「為什麼它會停在那裡」。

**根因是我自己的程式碼少了一段。** 客戶端在同一個位置不會停。

這跟 18,000 幀那次是同一個病：
第一次我記錄「我查不到」，第二次我寫了一個「量測過的補丁」。
**兩次都是因為沒有去讀客戶端怎麼做。**

唯一有效的動作是打開 `MapleCharacter.cs:824-843` 看那 20 行。
那 20 行我現在讀了，而且它推翻了我之前寫下的兩個「解釋」。
