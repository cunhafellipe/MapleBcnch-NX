## 二、根因：我的模型從一開始就是錯的

一直沒去讀 MapleNecrocer 的實際移動邏輯，只靠 scout 給的常數表猜。
剛讀了 `MapleCharacter.DoMove`（第 519 行起），它做的是：

```csharp
// 角色持有「當前 foothold」FH，不是每步去查地面
Direction = GetAngle256(X2, Y2, X1, Y1);
X += (float)(Sin256(Direction) * SpeedL);
Y -= (float)(Cos256(Direction) * SpeedL);   // 沿 foothold 的方向走

// 走到端點才換下一段
if ((X <= FH.X1) && (FH.PrevID != 0) && (!FH.IsWall()) && (!FH.Prev.IsWall()))
{
    FH = FH.Prev;
    X = FH.X2;
    Y = FH.Y2;
}
```

**三個關鍵差異：**

1. **角色沿著 foothold 的角度移動**，`Y` 由 `Cos256(角度)` 決定，
   不是「先橫移再查地面」。
2. **到端點才切換 foothold**（`X <= FH.X1`），不是每步重新查詢。
3. **不會穿過斜坡**，因為它從來不需要判斷「腳下有沒有地面」——
   它站在 foothold 上，沿著它走，走到頭才換下一個。

我做的則是「每步查 `FindBelow` 找腳下的地面」——
**這個模型在斜坡上必然不穩**，因為斜坡的表面每 px 都不同，
而我的查詢是逐點取樣。我修的六個 bug 全都是這個錯誤模型的**下游症狀**。

## 六、工作方向（重新收束）

### 立刻停止的

**不要再修 `FindBelow`。** 它是正確的查詢，只是我的**模型**用錯了它。
繼續在查詢上加容差（reach、tolerance、Ceiling）只會製造更多
「碰巧在這張地圖上對了」的程式碼。

### 該做的

**重寫 `CharacterPhysics`，採用 MapleNecrocer 的模型：**

```
角色狀態 = 當前 foothold（FH），不是 (x, y) + 每步查詢

每一步：
  1. 沿 FH 的角度移動：X += sin(angle) * speed
                      Y -= cos(angle) * speed
  2. 若 X 越過 FH 的端點 → FH = FH.Next（或 Prev），並把位置設為新端點
  3. 若沒有下一段 → 這就是鏈的盡頭，回報
```

好處：**不再需要 `FindBelow` 判斷「腳下有沒有地面」**，
斜坡問題自動消失，因為角色從來沒有「腳下」這個概念。

### 必須先確認的

1. **Walk speed 的真實值。** 從 `MapleCharacter.DoMove` 讀是
   `SpeedL += 1.5f`、上限 `2.5f`、`SpeedL -= 0.25f` 減速。
   這與 scout 給的 0.2/4 不是同一組。**以原始碼為準。**
2. **角度計算**：`GetAngle256` + `Sin256`/`Cos256` 是 256 分度查表。
   要確認本專案是否也需要同樣的離散化，還是用浮點斜率即可
   （視覺誤差 < 1px 的情況下應該沒差）。
3. **座標系**：`Y -= cos(...)` 表示 Y 向下為正，與本專案一致。
   但 `Player.Offset.Y = -79` 這個偏移要先釐清。

### 收束原則

**每一輪只做一件事，做完就驗收。** 這一輪我同時改了
`FindBelow`、落地判定、移動順序、容差——四個變數一起動，
結果每個都無法單獨歸因。

**驗收標準寫死**：角色走過 20 張真實地圖，每一點的 Y 都與
probe 查到的表面相差 ≤ 4px，且沒有一張地圖掉出地圖。

## 七、這一輪的教訓

**在修之前先讀原始碼。**

我派了 agent 去讀 MapleNecrocer，拿回一張常數表，然後就開始寫程式。
那份表是對的，但它給的是 `JumperSprite` 的預設值，不是 `Player` 的。
而**移動的模型**——沿 foothold 走、到端點才換段——根本不在那份表裡，
卻是整個機制的核心。

花了一整輪去修一個從一開始就不該寫的模型，
根源是「拿到常數就以為懂了」。

**與 §4.1、§6 同型：先確認自己的前提。**
