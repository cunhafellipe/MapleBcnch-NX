## 第一段（08:00–11:00）：對齊客戶端

### 08:26–08:59：一個查不到的問題

`610030510.img` 走完 18,000 幀（上限），`fellOut=false`，`reason` 空白。
地圖寬 2,068px，走完只需 827 步。

我讀了五次自己的程式碼、試了三種修法，做了一個決定性實驗
（`MaxFallFrames` 120→3，仍走滿 18,000），確認那段程式碼沒執行，
然後**寫文件記錄「我查不到」並停下來**。

使用者說「為何源碼都給你了，你卻好像找不到方向」——他說對了。
答案是 `MapleCharacter.cs:793-801` 的一行：`FallEdge = -999999`
預設永不觸發，而客戶端從不靠計時器中止。

**那個 18,000 幀不是錯誤，是沒有錯誤的成功。**
我驗證的一直是「會不會爆」，從沒驗「結果對不對」。

### 09:21：修對了，但方向錯了

三個 scout 審計客戶端 17,886 行，產出 32 項差距，我修了 4 項：

```csharp
VelocityY = -JumpHeight;   // 9.5，不是 -JumpSpeed(0.6)
// 峰值 0.3px → 80px
FH.Z = Iter.Text.ToInt();  // layer 索引，不是 IntegerAt("z")
jsJumping 與 jsFalling 分開
```

分布大幅改變：掉落 2509→415、邊緣 1521→3506。

**這個改變是可解釋的，所以是進步。**但那時我以為問題只是「缺功能」。

### 09:54–10:09：兩次判準修正

第一次（怪物 AI）：使用者說「他有的我就要有」。
我理解成「補完缺的」——**忘了另一半是刪掉我憑空發明的**。
於是刪掉 `Reach = 60`（客戶端從不讀玩家位置）與
`RespawnFrames = 600`（客戶端沒有重生）。

**這兩件會生產遊戲裡不存在的事實，比缺功能更危險。**

第二次：使用者問「你真的詳細檢視過參考專案嗎？我感覺有些問題不該存在」。

審計報告自己寫了：

```
FindWallL :153-181 (Y1>=P.Y && Y2<=P.Y — unsatisfiable for typical walls)

```

我讀過了，沒停下來，把它列進 25 項計畫。
**「客戶端有的我就要有」的前提是「客戶端在跑」。**

### 10:19：實測證明差距有多大

地圖邊界原本四邊都用 foothold 極值。客戶端兩個分支都不是：

```csharp

無 VRLeft → Bottom = -centerY + MapHeight - 55   ← 也不是 foothold 極值
```

實測 `f1/Map/Map2/200090410.img`：

| 邊界 | 我的 | 客戶端 VR | 差 |
|---|---|---|---|
| Left | -322 | -420 | +98 |
| Right | 149 | 380 | **-231** |
| Top | -1166 | -1320 | +154 |
| Bottom | -443 | -230 | -213 |

**四邊全錯，最大 231px。**修正後完全相符。

### 10:56：P0，而且測試全綠

`CharacterPhysics.Walk()` 的交接被掛在 `reachedEnd` 上，
而它只在鏈尾為真——**鏈中間永假**。

```
修正前：300 步走過 1 段 foothold ['177']

```

**那時 23/23 acceptance、10,732 次零錯誤。**
沒有一條規則在看「角色走了多遠」。

順帶：修好後 `save verifies` 也從失敗變通過——
那個「早於本輪」的失敗，成因是檔案鎖：交接 bug 讓角色卡住不放。
**修一個物理 bug 順帶修好一個存檔 bug，根因是同一個。**

## 第二段（12:32–13:14）：轉向

### 12:32：工程分析，改變方向

使用者說：「我需要你不是盲目地寫代碼或是抄，是學會為什麼這樣說，
跟原本有甚麼差別，原本是甚麼，參考項目是甚麼，為什麼人家可以。」

我讀客戶端原始碼，歸納出它的三個設計決定，並找到我為什麼一直偏離：

| 客戶端 | 我重寫成 | 後果 |
|---|---|---|
| `if ((X <= FH.X1) && ...)` 位置判斷 | `if (!reachedEnd)` | 角色卡住不動 |
| 行走區塊無 `JumpState` 判斷 | `Fall()` 純垂直 | 角色懸停半空 |
| `VelocityY = -JumpHeight` | `-JumpSpeed` | 跳躍 0.3px |
| `FallEdge = -999999` 預設永不觸發 | `_x >= X2` | 每條鏈最後一幀掉落 |

**四次全部是同一個錯誤：把照抄變成了重寫。**

而客戶端物理段只有 289 行，外部依賴只有 **8 處 `Keyboard.KeyDown`**，
其餘 0 處音效動畫。**機械式替換參數就能照抄。**

結論寫進計畫：
> **「客戶端有的我就要有」的前提是「客戶端在跑」。**
> **驗收規則比照抄更重要**——因為照抄完我會用同樣的方式改壞它，
> 而沒有規則能抓到。

### 12:57：第 1 步，規則改了三次才對

| 版本 | 規則 | 結果 |
|---|---|---|
| v1 | 跨 1 段 foothold = 沒動 | **誤報**：整張地圖本來就是一條 750px 的線 |
| v2 | 且宣稱抵達邊緣 | **還是有**：長線本來就能合法抵達 |
| v3 | 且沒花太多時間 | **還是有**：長線本來就需要很多時間 |
| v4 | **幾何檢查** | ✅ 通過 |

**訊號不是距離、不是段數、不是時間，是幾何。**
「角色說它在 14 上，那裡真的有 14 嗎」——用 `/probe` 直接問地圖。

v4 還踩到陷阱：trace 結尾可能正在下落，那時腳下本來就沒有 foothold。
規則只檢查站在地面上的幀。

**規則抓到一個真 bug**：`260020620.img` 宣稱走完 100%，
卻全程站在一個只跨 51px 的 foothold 上。

兩層根因：`FindLinked` 只用 id 查找（id 只在 layer 內唯一），
以及交接失敗時沒有東西限制 X。

**規則必須先證明抓得到東西。**我故意把兩個已知 bug 放回去，兩次都叫了。

### 13:14：照抄第一批

| 項目 | 客戶端 | 我原本 |
|---|---|---|
| 地面探測 | `FindBelow(X±10, Y-5)` 的 Z | 腳下的 Z |
| 牆探測 | `(X±4, Y-4)` | `(X±4, Y)` |
| EdgeSlack | 右 +5 / 左 -10 | 統一 10 |
| 地圖邊界 | `Map.Left+20` 夾制 | **完全沒有** |
| 掉落邊界 | **沒有垂直的** | `FallMargin = 400` 憑空 |

邊界夾制加上後，「卡住」從 266 暴增到 2,777——那是因為
**撞到地圖的牆被誤判成卡住**。修正分類後卡住回到 265，
邊緣 1991→2512。
