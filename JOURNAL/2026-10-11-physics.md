## 一、常數不是猜的

派兩個 agent 讀 MapleNecrocer 原始碼，取回實際數值：

| 常數 | 值 | 出處 |
|---|---|---|
| `JumpSpeed` | 0.6 | `MapleCharacter.cs:136` |
| `JumpHeight` | 9.5 | `MapleCharacter.cs:137` |
| `MaxFallSpeed` | 8 | `MapleCharacter.cs:138` |
| `Acceleration` | 0.2 | `SpriteEngine.cs:1519` |
| `Decceleration` | 0.2 | `SpriteEngine.cs:1520` |
| 固定步長 | 0.016666668f（1/60 秒） | `RenderFormDraw.cs:177` |
| 角色半寬 | 10 | `LadderRopes.cs:18-27` |

**尺度不是自由參數。** 客戶端以 60 Hz 每幀套用這些常數，
`0.2f` 的加速度等於 12 px/s²。套用到 100 ms 的步長上，
角色會慢五倍，每個常數都預設 `StepSeconds` 是 1/60——
所以模擬是固定步長，這是有原因的，不是習慣。

Y 軸向下增長，與 WZ 及本專案所有座標一致；MapleNecrocer 也是
螢幕向下，所以常數可以直接搬。

## 二、實測：角色真的走完了

```
101000200.img
  289 步 = 4.8 秒
  1118 / 1116 px
  抵達右緣 reachedEdge=true
```

新增 `CharacterPhysics.cs`，把鏈條檢查換成真正的物理：
角色有速度、有重力、會落地、會被牆擋住。

新增兩個端點：

- `POST /api/simulate/character` — 真的走一遍，回報軌跡
- `GET  /api/simulate/probe` — 查某個 X 上有哪些 foothold

`probe` 是因為「角色站在 y=119，我不相信」這個問題，
walk 自己的輸出答不了。

## 三、順帶修好一個真缺陷：鏈的斷點

原本鏈走到 `next=0` 就一律算通過。實測發現站不住腳：

- 站在**地圖右緣**結束 → 正常（`101000200` 的最後一個 foothold 在 x=570，
  正好是右界）
- 站在**開闊地**中間結束 → 角色會卡住

第一版修得太鬆：只判斷「有沒有前驅」，結果 100 張抽樣裡
**57 張被誤判成死路**，連好地圖都被冤枉。

第二版加了邊界條件：終點的 `Right` 要等於或超過地圖右緣才算正常。

修正後 100 張：

```
正常抵達邊緣   39
半路斷掉       20   （7% ~ 70% 之間，確實是中途卡住）
link stub      41
```

這 20 張是真的鏈斷在半路——`/validate` 抓不到這種，
因為 prev/next 本身沒有壞，是鏈的長度不夠。

## 四、⚠️ 發現一個還沒修的 bug

軌跡診斷（用 `probe` 逐點查）發現：

```
x=  16 y= 154 → 站在 foothold 6  (表面 -3019)
x=  40 y= 154 → 站在 foothold 7  (表面 -3024)
x=  88 y= 154 → 站在 foothold 8  (表面 -3019)
x= 136 y= 154 → 站在 foothold 83 (表面  -422)
```

角色在 y=154，卻「站」在表面 y=-3019 的 foothold 上。

**原因**：`FindBelow(x, y)` 回傳「y 之下最高的表面」。
當角色已經落到 y=154，而某個 foothold 的表面在 -3019，
那個 foothold 永遠在它下方，於是每一步都被選中，
角色就橫著走在幾千像素高的空中。

**這是 `FootholdPhysics.FindBelow` 的缺陷**，2026-10-11 那一輪寫的。
還沒修。

### 順帶：MapleNecrocer 自己也有這個問題

scout 的報告原文：

> FindBelow searches in raw list insertion order (WZ document order)
> and, on the first candidate, accepts it unconditionally without verifying
> it is at or below the query point — so the result depends on list order,
> not on a true "lowest foothold" search.

**我沒有複製這個錯誤**（我的版本確實檢查 `sy > y` 就跳過），
但我的版本有同一類的問題：沒有「已經落到這裡以下就該繼續落」的邏輯。

### 這是什麼樣的 bug

不是視覺問題。角色在幾千像素高的空中走完整張地圖，
`reachedEdge=true` 看起來像成功。**這正是「實測通過」騙人的情況**：
它確實走完了，但走在錯誤的地方。

**下一輪第一件事就是修這個。**
